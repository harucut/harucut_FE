# 고도화 구현 진행 상태

- 기준 기획: 「하루컷 제품 고도화 기획서」 R5(2026-10-26). 판정은 [plan-review-r5-verdict-2026-10-26.md](./plan-review-r5-verdict-2026-10-26.md).
- 범위: P0~P5 전체. 사용자 지시는 「설계에 나온 것을 전부 끝까지 하되, 배포는 하지 않고 develop 까지만」이다.
- 백엔드는 하루컷 백엔드 저장소에서 따로 진행한다. fork `harucut/Harucut` 의 develop 대상이다.
- 상태 표기
  - **완료**: develop 에 merge 됐고 자동 검증을 통과했다.
  - **PR**: 올렸지만 아직 merge 하지 않았다.
  - **진행**: 작업 중이다.
  - **대기(BE)**: 백엔드 계약이나 구현이 먼저 필요하다.
  - **대기(사용자)**: 접근 권한이나 사업 결정이 필요하다.
- 「완료」는 develop 기준이다. 운영 배포와 실기기 확인은 따로 적는다.

## 운영 반영 조건

develop 은 운영보다 앞서 있다. main 반영은 고도화 기획이 끝난 뒤 한 번에 하고, 그때 아래 순서를 지킨다.

- 백엔드가 먼저 나간다. 프론트 #527·#528 은 운영 백엔드에 없는 API(자산·서버 초안)를 부른다.
- 백엔드 fork #14 부터는 운영에 Flyway 를 켠 뒤에만 배포할 수 있다. 운영 스키마 대조 → baseline(ADR-0005 §3)이 먼저다.
  꺼진 채로 내보내면 Hibernate update 가 옛 유니크를 지우지도, user_id 의 NOT NULL 을 풀지도 못한다.
- 배경 fit(F1-1)은 합성 Lambda 재배포가 있어야 결과에 반영된다.
- 행사 세션 발급 빈도 제한(분당 30)은 IP 기준이다. 프론트 BFF 는 참가자 IP 를 `x-forwarded-for` 로 넘긴다(#523).
  백엔드에 신뢰 프록시 설정(`server.forward-headers-strategy` + 내부 대역)이 있어야 그 값을 쓰고, 신뢰 대역 밖의 값은 버려야 위조로 제한을 피하지 못한다.
  부스 연결 코드 교환(분당 30)과 틀린 결과 토큰(분당 30)도 같은 전제다.
- 백엔드 migration 은 V23 까지다(V9 참가자, V10 부스, V11 초대·EventGrant·감사, V12 사진 삭제, V13 묶음, V14 문의·계약·이용권·사용량,
  V15 보관 종료, V16 웹훅 수신, V17 프레임 발행 번호, V18 S3 삭제 예약, V19 프로젝트·기본값, V20 운영 담당, V21 상시 캠페인·한도 알림,
  V22 기업 총량 배분, V23 여러 행사 묶음). 모두 Flyway 편입 뒤에 적용한다.
- V20 은 공간 역할 enum 에 OPERATOR 를 더한다(workspace_membership·workspace_invitation). V22 는 usage_reservation·usage_ledger 유니크를
  바꾸고(새 키를 먼저 더한 뒤 옛 키를 지운다) 생성 칼럼 active_allocation 과 유니크를 더한다. V23 은 export_job.event_id 를 NULL 허용으로 바꾸고
  workspace_id 를 기존 행에서 채운다. 운영 스키마 대조에 이 셋을 넣는다.
- 기존 이용권은 한도 알림(80·95·100%)을 소급하지 않는다. 배포 뒤 다음 확정 때 처음 기록된다.
  V14 의 `uk_contract_evidence` 는 기존 계약에 같은 결제 근거가 있으면 실패한다 — 먼저 대조한다.
- 게시·합성에 이용권이 필요해졌다(P2B-5). 이 변경 전에 게시된 LIVE·CAPTURE_CLOSED 행사가 있으면 배포 전에 수동 부여(ManualGrant)를 준다.
  없으면 배포 직후 촬영이 ENT-002 로 막힌다.
- 결제 웹훅 검증기가 mock 이면 local·test 밖에서는 `PAYMENT_MOCK_ALLOWED=true` 없이 기동하지 않는다. PortOne 으로 켜려면 웹훅 비밀·API 비밀·상점 id 셋이 필요하다.
- 보관 종료 배치(매일 04:00)의 첫 실행은 오래된 행사 결과를 한꺼번에 정리할 수 있다. 운영 규모를 보기 전에는 cron 을 꺼 두고 관찰한다.
- 배포 뒤 `harucut.s3.deletion.abandoned` 가 0 이 아니면 `s3_deletion.last_error` 를 본다(S3 권한·버킷 문제).
- 미참조 자산 정리(#21)의 첫 실행은 그동안 쌓인 미참조 자산을 지운다. 규모를 모르므로 운영 반영 전에 cron 을 끄거나(`-`)
  max-per-run 을 낮춰 첫 실행을 관찰한다.
- 시스템 기본 프레임은 배포 뒤 관리자가 프레임마다 발행 API(`POST /api/admin/frames/{id}/versions`)를 한 번씩 불러야 행사에서 고를 수 있다.

## AGPL 확인 결과 (F0-2)

- `@imgly/background-removal` 1.7.0 의 라이선스는 AGPL-3.0 이다(설치본 LICENSE.md).
- 쓰는 곳은 편집기 자산 누끼 하나다(`lib/backgroundRemoval.ts` 동적 import → `themeEditorStore.removePhotoBackground`).
  촬영 칸 누끼는 MediaPipe(Apache-2.0)라 무관하다.
- 모델·wasm 은 설정(publicPath)이 없어 IMG.LY CDN 에서 받는다.
- 고를 수 있는 길: ① AGPL 의무 이행(웹 클라이언트 소스 공개 등) ② IMG.LY 상용 라이선스 ③ 대체(예: 사람 누끼는
  MediaPipe 재사용, 사물 누끼는 허용 라이선스 모델 검토). 사용자 결정 전에는 코드를 바꾸지 않는다.
