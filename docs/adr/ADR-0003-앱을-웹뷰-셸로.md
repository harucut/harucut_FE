# ADR-0003 — 앱을 웹뷰 셸로 바꾼다 (ADR-0001 대체)

- 상태: 채택
- 날짜: 2026-08-18
- 대체 대상: [ADR-0001 모바일 확장 전략](./ADR-0001-모바일-확장-전략.md)

## 무엇을 바꿨나

앱이 자기 화면을 그리지 않는다. 웹을 그대로 띄우고, 웹이 못 하는 것만 네이티브가 맡는다.

| | 이전 | 이후(2026-08-18 시점) |
|---|---|---|
| 앱 화면 코드 | `screens/` 6,299줄 + components/store/lib 등 11,534줄 | 셸·브리지 383줄 |
| 라우트 | 19개(웹의 부분집합) | 1개(`app/index.tsx`) |
| 네이티브가 맡는 것 | 전부 | 사진첩 저장·공유 시트·햅틱·뒤로가기·딥링크 |

「383줄」은 결정 당시의 실측이다. 오늘은 957줄이다 — 아래 [「예산이 어긋난 자리」](#예산이-어긋난-자리--383줄--957줄) 참고.

## 왜

**앱은 대등한 구현이 아니라 뒤처진 복제본이었다.** 앱 라우트 19개는 전부 웹에 1:1 로 있었고
앱 전용 화면은 하나도 없었다. 반대로 웹에는 핵심 단계인 `/decorate`(네컷 꾸미기)가 더 있었다.

> 이후 기록: `/decorate`(네컷 꾸미기)와 그 전용 업로드 경로 `/upload` 는 2026-08 에 제거됐다(`bbfdcbf`).
> 백엔드가 완성 이미지를 등록하는 API 를 없애고 서버 합성(원본 4장 → 서버가 그림)으로
> 계약을 바꾸면서, 이미 합쳐진 그림에 스티커를 얹는 결과물을 남길 자리가 사라졌기 때문이다.
> 단 **갤러리 업로드 자체는 나흘 뒤 다른 라우트로 되살아났다**(`09a13f0`, `apps/web/app/shoot/upload/`).
> 「사진 업로드가 사라졌다」로 읽으면 틀린다.
> 위 판단은 그 시점(2026-08-18)의 사실을 근거로 한 것이라 그대로 둔다.

두 벌을 유지하는 비용이 실측으로 드러났다 — 최근 300 커밋 중 웹·앱을 건드린 196개 가운데
**45개(23%)가 같은 변경을 두 번 구현한 것**이었다. 그리고 두 번 만드는 동안 계속 어긋났다:

- 소셜 로그인 로고 크기: 웹 18/20/22px vs 앱 20/26/30px
- 네이버 버튼색: 웹 `#007A3D` vs 앱 `#03C75A` (둘 다 규정 위반이었다)
- 버튼 순서: 웹 구글부터 vs 앱 카카오부터
- 비회원 체험 범위와 안내 문구

웹의 모바일 뷰는 애초에 모바일 우선으로 짜여 있었다 — 기본 컨테이너가 `max-w-md` 이고
`lg:` 에서 데스크톱으로 확장되며, 앱의 하단 5탭과 같은 규격의 `MobileTabBar`(74px 바 +
54px 촬영 FAB)가 이미 있었다. 즉 "앱처럼 보이는 웹"이 이미 존재했다.

## ADR-0001 을 뒤집는 이유

ADR-0001 은 "웹이 브라우저 전용 API(react-konva, Canvas, getUserMedia)에 깊게 의존해서
앱 UI 를 따로 설계한다"고 적었다. 그 전제가 반대로 뒤집혔다 — **그 브라우저 API 들이
WebView 안에서 그대로 돈다.** 따로 설계할 이유가 아니라 웹을 그대로 쓸 이유가 됐다.

## 경계선

네이티브에 남기는 것은 **웹이 할 수 없는 것**뿐이다.

- **사진첩 저장** — 웹 표준에 사진첩 쓰기 API 가 없다. WebView 에서는 `<a download>` 가
  조용히 아무 일도 안 한다(안드로이드는 download 속성 무시 + blob 은 DownloadListener 로도
  못 받음, iOS 는 저장 UI 자체가 없음).
- **공유 시트** — 안드로이드 WebView 에 `navigator.share` 가 없다.
- **햅틱** — 웹 `navigator.vibrate` 는 iOS 에서 동작하지 않는다.
- **하드웨어 뒤로가기** — 셸이 처리하지 않으면 어느 화면에서든 앱이 통째로 닫힌다.
- **딥링크(`harucut://`)** — 소셜 로그인 복귀 경로.

> 위 다섯은 **2026-08-18 에 이렇게 정했다**는 기록이다. **현행 목록의 소유자는
> `docs/mobile-shell.md` 이고, 그 뒤로 목록이 달라졌다.** 두 가지만 짚어 둔다.
> ① 딥링크는 아직 **구현되지 않았다** — `app.json` 에 `scheme: "harucut"` 이 등록돼 있을 뿐,
> `apps/mobile` 전체에 들어오는 URL 을 받는 코드가 없다(`Linking.useURL`·`getInitialURL`·`url`
> 이벤트 0건. `expo-linking` 은 나가는 `Linking.openURL` 두 자리에만 쓴다). 이 경로를 쓸
> OAuth 일회용 코드 흐름 자체가 아직 백엔드 요청 상태다.
> ② 반대로 이 목록에 없는 **알림**과 **상태바 색**은 셸이 실제로 맡고 있다.

프로토콜은 `apps/web/lib/nativeBridge.ts` ↔ `apps/mobile/lib/native-bridge.ts` 한 쌍이다.
바꾸려면 양쪽을 같이 고쳐야 한다.
(어느 URL 이 이 브리지를 부를 수 있는지 판정하는 규칙은 `apps/mobile/constants/shell.ts` →
`packages/shared/src/shell-origin.ts` 에 따로 있다. 브리지의 문이므로 함께 본다.)

## 예산이 어긋난 자리 — 383줄 → 957줄

> 2026-09-02 실측. **결정은 그대로 유효하다.** 이 절은 이 문서가 틀린 숫자를 주장하지 않게 하려고
> 붙인 기록이고, 다음 사람이 셸에 상태를 더 얹기 전에 한 번 멈춰 서라고 남긴 것이다.

| | 결정 당시(`19e1adc`) | 오늘 |
|---|---|---|
| `apps/mobile/components/harucut-web-shell.tsx` | 235 | 569 |
| `apps/mobile/lib/native-bridge.ts` | 148 | 388 |
| 합 | **383** | **957** (약 2.4배) |

`apps/mobile/constants/shell.ts`(77줄)까지 넣으면 1,034줄이다. 라우트는 여전히 1개이고 앱 화면도
늘지 않았다 — **늘어난 것은 전부 상태**다. 지금 셸 컴포넌트 하나에 `useState`/`useRef` 가 9개 있다.
증가분은 대부분 위 「경계선」이 열거하지 않은 관심사다.

1. **전송 세션** — 모듈 수준 `transfers` Map + TTL(`TRANSFER_TTL_MS` 120초) + 용량 상한
   (`MAX_TRANSFER_BYTES` 24MB, 조각·문자 수 파생 상한) + 셸의 명시적 취소(`cancelTransfers`).
2. **재장착과 재시도 예산** — `webViewSession` 키로 WebView 를 통째로 다시 올리는 `remountWebView`,
   콘텐츠 프로세스가 거듭 죽을 때 쓰는 재시도 한도(`MAX_CONTENT_PROCESS_RELOADS` = 2),
   그리고 그 한도를 넘겼을 때 띄우는 **네이티브 실패 화면**(「연결에 실패했어요」 + 다시 시도 버튼).
   즉 「앱이 자기 화면을 그리지 않는다」에는 예외가 하나 있다.
3. **OAuth 뒤 기록 정리** — `historyResetPendingRef` 로 로그인 왕복이 끝난 뒤 히스토리를 비우고,
   그 직후 도착하는 `canGoBack` 을 한 번 무시한다. 안 하면 뒤로가기가 로그인 화면으로 돌아간다.
4. **나가는 오리진 판정** — 우리 웹인가 / OAuth 흐름인가 / 밖으로 보낼 링크인가를 갈라
   외부 브라우저로 내보내는 처리.
5. 그 밖에 **알림 서브시스템**(권한·로컬 알림·안드로이드 채널)과 **상태바 테마**.

### 전송 기계를 왜 못 지우나

가장 큰 덩어리인 1번은 없앨 수 있는 종류가 아니다. **백엔드에 비회원 경로가 없기 때문이다** —
합성도 프레임 저장도 전부 `/api/auth/` 아래다(도는 서버 OpenAPI 확인). 그래서 비회원의 결과물은
서버에 URL 로 존재한 적이 없고, 브라우저가 그린 blob 이 곧 최종본이다(`composeFramePng`).
그 blob 이 사진첩에 닿는 길은 브리지뿐이다. 그리고 수 MB 짜리 base64 를 `postMessage` 한 번에
실으면 WebView 가 버벅이거나 문자열이 잘리므로, 쪼개 보내야 하고, 쪼개면 **조립 상태**가 생긴다 —
그 상태에 수명·상한·취소가 붙은 것이 1번이다. 회원 결과물은 https URL 이라 주소 한 줄이면 끝난다.

정리하면 이 예산 초과의 뿌리는 아래 「아직 열려 있는 것」 2번이다. 비회원 합성 경로가 서버에 생기면
1번은 실제로 줄어든다. 그 전까지는 지우면 비회원이 결과물을 못 가져간다.

## 카메라를 네이티브로 되돌릴 여지

촬영은 지금 WebView 안의 `getUserMedia` 가 한다. 화질 천장은 이쪽이 낮다 —
합성 캔버스가 4000×6000(24MP), 슬롯 1700×2400(4.08MP) 규격인데 `getUserMedia` 는
안드로이드 최선에서도 컷당 1.65MP 다.

다만 **이 전환이 화질을 떨어뜨리지는 않는다.** 이전 앱은 최종 결과물을
`captureRef(미리보기 View)` 로 만들었고, 그건 화면 해상도에 묶여 있었다(기기가 작을수록 낮음).
즉 네이티브 카메라의 이점을 이전 앱도 실현하지 못하고 있었다.

화질을 실제로 올리려면 촬영만 네이티브로 되돌리면 된다. 브리지에 `openCapture` 를 추가하고
결과를 웹으로 돌려주는 형태다. 그때는 `expo-camera` 를 다시 넣되
`takePictureAsync({ quality: 1 })` + `pictureSize` 지정 + `skipProcessing` 미사용이어야 한다
(`skipProcessing: true` 면 quality 가 무시되고 EXIF 방향이 깨진다 — 이전 코드의 실수였다).

## 아직 열려 있는 것

정본은 `docs/app-shell-backend-requests.md` 다. 지금 그 문서가 세는 것은 **세 가지**이고
(아래 둘 + 푸시 알림용 기기 토큰 등록), 이 결정과 직결된 것은 둘이다.

1. **OAuth 세션을 앱으로 넘기는 일회용 코드** — 없으면 앱에서 구글 로그인이 불가능하다
   (구글이 임베디드 웹뷰를 `disallowed_useragent` 로 차단한다). 카카오·네이버는 지금도 된다.
2. **비회원·행사 참가자용 합성 경로** — 서버 합성이 전부 인증 경로 아래라,
   "참가자는 가입 없이 찍고 그 자리에서 가져간다"는 판매 문구가 서버 합성 전환 시 깨진다.
   위 「전송 기계를 왜 못 지우나」가 이 구멍의 비용이다.
