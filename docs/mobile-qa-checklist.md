# 모바일 QA 체크리스트

`apps/mobile` 작업을 완료로 판단하기 전에 아래를 직접 확인한다.

## 범위

- 모바일 변경은 `apps/mobile` 중심으로 확인한다
- 웹 연동 변경이 있으면 `apps/web` 변경과 웹 검증도 함께 확인한다
- 직접 확인한 기준으로만 완료를 판단한다

## 화면 확인

- `home`
  - 첫 진입 흐름이 자연스럽다
  - 주요 CTA가 바로 보인다
  - 텍스트가 겹치거나 잘리지 않는다
- `shoot` (`shoot/index` → `shoot/capture` → `shoot/select` → `shoot/result`)
  - 카메라 권한 안내 문구가 명확하다
  - 버튼 배치가 한 손 사용 기준으로 무리가 없다
  - 촬영 중에는 프레임이 씌워지지 않고 슬롯 비율만 반영된다 (프레임리스 촬영)
  - 프레임은 선택·결과 단계부터 보인다
- `theme` (`theme/index` → `theme/sticker` 테마 에디터)
  - 프레임 타입 선택과 저장된 프레임 불러오기가 동작한다
  - 스티커 배치: 추가, 이동, 크기 조절, 회전, 삭제가 손가락 조작으로 자연스럽다
  - 누끼 토글: 칸별로 켜고 끌 수 있고 미리보기에 즉시 반영된다
  - 배경 선택: 단색 스와치와 이미지 선택이 동작하고 사진 뒤에 깔린다
  - 저장: 저장 후 `theme`로 돌아가고 목록에 반영된다
  - 삭제: 확인 절차가 있고 삭제 후 목록에서 사라진다
  - 저장한 프레임을 촬영에서 다시 고를 수 있다
- `history`
  - 빈 상태와 데이터 상태 모두 자연스럽다
  - 카드와 리스트의 가독성이 유지된다
- `mypage`
  - 계정, 설정, 로그아웃 흐름이 명확하다
  - 개발용 정보가 사용자 화면에 노출되지 않는다
- `pricing`
  - 비교표가 5행이다: 커스텀 프레임 / 사진 보관 기간 / 보정 / 광고 제거 / AI (추후)
  - 각 행의 값이 웹 `apps/web/constants/plans.ts`와 정확히 같다
  - `동영상`, `워터마크` 행이 남아 있지 않다
  - 결제는 미오픈이므로 플랜 변경 CTA가 "준비 중"으로 표시된다
  - 서버 등급(BASIC/PLUS/PRO)이 화면에 그대로 노출되지 않고 카드 이름(Free/Plus/Pro)으로 보인다
- `terms`, `privacy` (법적 고지)
  - 본문이 `@harucut/shared`의 `legal.ts` 내용과 같다 (웹과 동일 문구)
  - 긴 문서에서 스크롤과 제목 구조가 읽기 편하다
  - 사업자 정보와 고객센터 연락처가 최신 값이다
- `oauth2/callback` (소셜 로그인 콜백)
  - KAKAO, NAVER, GOOGLE 각각 성공 시 원래 화면으로 복귀한다
  - 실패나 취소 시 로그인 화면으로 돌아가고 에러 문구가 이해 가능하다
  - 탈퇴 신청 계정(`DELETED_REQUESTED`)은 재등록 확인 절차를 거친다
  - 차단 계정(`BLOCKED`)은 진입하지 못하고 안내가 보인다

### 로그인 뒤 뒤로가기 (안드로이드 실기기·에뮬레이터)

콜백은 `window.location.href` 로 홈을 열어 기록에 남는다. 셸이 정리하지 않으면 뒤로가기가
콜백으로 돌아가고, 콜백은 이미 소비한 `redirectTo` 대신 다시 홈으로 보낸다 — 홈과 콜백을
오가며 앱을 닫을 수 없다.

- 로그인을 마치고 하드웨어 뒤로가기를 한 번 누른다
  - 콜백 화면(`로그인 처리 중`)이 다시 보이지 않는다
  - 앱이 정상적으로 닫힌다 (뒤로가기가 먹통이 아니다)
- 로그인 뒤 다른 화면(`history` 등)으로 이동한 다음 뒤로가기를 누른다
  - 직전 화면으로 정상 복귀한다 (일반 웹 기록은 그대로 동작한다)
  - 거기서 한 번 더 누르면 콜백이 아니라 앱 종료로 이어진다
- 제공자 화면에서 로그인을 **취소**하고 뒤로 나온다
  - 콜백을 거치지 않았으므로 기록이 그대로다 — 로그인 화면과 이전 화면으로 정상 복귀한다
- 로그인 실패(`상태 확인 실패`)로 로그인 화면에 돌아온 뒤 뒤로가기를 누른다
  - 콜백으로 되돌아가 같은 실패를 반복하지 않는다
- 로그인 직후 화면에서 **주소가 바뀌지 않는 모달**(뒤로가기로 닫는 종류)을 연다
  - 뒤로가기 한 번에 모달만 닫힌다 — 앱이 닫히지 않는다
  - 모달이 닫힌 뒤 한 번 더 누르면 그때 앱이 닫힌다

## 사용자 경험 확인

- safe area가 깨지지 않는다
- 상단과 하단 여백이 어색하지 않다
- 텍스트 눌림, 겹침, 버튼 밀림이 없다
- 색 대비가 충분하다
- 주요 버튼 터치 영역이 너무 작지 않다
- 로딩, 빈 상태, 에러 상태가 시각적으로 구분된다

## 앱 셸 브리지 확인

셸(`apps/mobile/lib/native-bridge.ts`)이 웹에 답을 돌려주지 못하면 웹 버튼이 타임아웃까지 묶인다.
답은 `injectJavaScript` 로 나가므로 **셸이 WebView 를 잡고 있는지**(`ref`)가 전제다.

### 답이 오는가 (전 항목 공통)

버튼을 누르고 **초 단위로** 결과가 보여야 한다. 60초·120초를 기다린 뒤 `네이티브 응답이 없어요.`
가 뜨면 답이 아예 오지 않은 것이다.

- 사진첩 저장(`shoot/result`) — 저장 직후 성공/실패 문구가 바로 뜬다
- 공유(`shoot/result`) — 공유 시트를 닫으면 버튼이 바로 원래 상태로 돌아온다
- 알림 켜기(`mypage`) — 권한 대화상자를 닫는 즉시 결과가 반영된다
- 회원가입 화면의 약관·개인정보처리방침 링크(`target="_blank"`)를 누른다
  - 같은 WebView 안에서 문서가 열린다 (아무 반응 없이 무시되지 않는다)
- 공유 시트를 띄워 둔 채 닫고 **곧바로** 소셜 로그인으로 넘어간다
  - 제공자 로그인 화면이 그대로 뜬다 (셸의 답은 우리 오리진에만 넣는다 — 남의 문서에서
    스크립트가 돌지 않는다)

### 사진첩 저장

- 만료된 사진 URL(403)로 저장하면 실패 문구가 뜬다
- 실패한 뒤 캐시에 그 파일명이 남지 않는다 (재시도해도 쌓이지 않는다)
- 24MB 를 넘는 이미지를 저장하면 `이미지가 너무 커서 저장할 수 없어요.` 문구가 뜬다
- 사진첩에 들어간 파일 이름이 화면의 표시 이름 그대로다 (임시 폴더 이름이 새지 않는다)

### 이름이 같은 두 장을 동시에 저장할 때 (`history`)

기록 화면은 **누른 카드의 버튼만** 잠그고 이름이 같은 기록도 허용한다. 임시 경로를 표시 이름
하나로 정하면 두 요청이 같은 파일을 쓰고 지운다 — 남의 사진이 사진첩에 들어간다.

- 이름을 같게 바꾼 기록 두 개를 만들고, 앞의 저장이 끝나기 전에 뒤의 저장을 누른다
  - 둘 다 성공 문구가 뜬다 (한쪽이 실패하면 회귀다)
  - 사진첩에 **서로 다른 두 장**이 들어간다 (같은 사진이 두 번이면 회귀다)
- 저장을 여러 번 반복한 뒤 앱 캐시 용량이 계단식으로 늘지 않는다 (임시 폴더가 남지 않는다)

### 사진첩 권한을 거절했을 때 (`shoot/result`, `history`)

권한 거절은 **재시도로 풀리지 않는다.** 네이티브는 무엇을 해야 하는지 아는 문구를 돌려주고
(`native-bridge.ts` 의 `ensurePermission`), 웹은 `code` 가 붙은 실패만 그 `reason` 을 그대로
띄운다 — `apps/web/lib/nativeBridge.ts` 의 `NativeSaveError`·`getNativeSaveErrorMessage`,
던지는 자리는 `lib/canvas/composeFrame.ts` 의 두 다운로드 함수다. 일반 `Error` 로 바꾸면
`getUserFacingApiErrorMessage()` 가 message 를 버려 폴백 문구로 덮인다.

- 권한을 거절한 채 저장을 누른다 (`code: photo-permission-denied`)
  - `사진첩 저장 권한이 필요해요.` 가 그대로 뜬다
- 시스템 설정에서 사진 접근을 끄고(다시 묻지 않는 상태) 저장을 누른다
  (`code: photo-permission-blocked`)
  - `설정에서 사진 접근을 허용해 주세요.` 가 그대로 뜬다 — `잠시 후 다시 시도해 주세요.` 로
    덮이면 회귀다
- 권한과 무관한 실패(비행기 모드 등)에서는 네이티브 영문 원문이 화면에 나오지 않는다
  (`code` 가 없는 실패는 폴백 문구로 덮는 것이 맞다)

### 저장 도중 화면이 움직일 때

같은 문서 안의 이동(SPA)과 문서 교체를 **가려서** 끊는다. 안드로이드는 둘 다 같은 이벤트로
오기 때문에 실기기 확인이 필요하다.

- 게스트로 저장을 누른 직후 `로그인하고 저장` 을 누른다 (같은 문서 안 이동)
  - 저장이 끝까지 진행된다 — `저장할 데이터를 받지 못했어요.` 가 뜨면 회귀다
- 저장을 누른 직후 **아래로 당겨 새로고침**한다 (문서 교체)
  - 그 요청은 버려진다. 다시 저장하면 처음부터 정상 진행된다
- 앱을 백그라운드로 보냈다 돌아와 WebView 가 다시 뜬 뒤 저장을 5~10회 재시도한다
  - 매번 정상 저장된다
  - Android Studio Profiler 또는 Xcode Instruments 에서 재시도마다 앱 메모리가 계단식으로
    올라가지 않는다 (끊긴 전송이 조각을 들고 남지 않는다)

### WebView 가 죽었다 살아나는 길

되살리는 방법이 플랫폼마다 다르다(`docs/mobile-shell.md`). 둘 다 확인한다.

- 안드로이드: 저장·촬영 결과 화면에 머문 채 렌더 프로세스를 죽인다
  (`adb shell ps -A | grep sandboxed_process` 로 PID 를 찾아 `adb shell kill <PID>`)
  - 흰 화면으로 남지 않고 **보던 화면**이 다시 뜬다
  - 그 뒤 하드웨어 뒤로가기를 누르면 먹통 없이 앱이 닫힌다 (새 WebView 는 기록이 비어 있다)
- iOS: 앱을 백그라운드에 두고 다른 무거운 앱을 열어 콘텐츠 프로세스가 회수되게 한다
  (시뮬레이터는 Debug → Simulate Memory Warning)
  - 돌아왔을 때 흰 화면이 아니라 보던 화면이 다시 뜬다
- 비행기 모드로 첫 진입해 `연결에 실패했어요` 를 띄운 뒤, 통신을 켜고 `다시 시도` 를 누른다
  - 실패했던 그 화면이 다시 열린다 (버튼이 무반응이면 회귀다)

### 실패 화면에서 빠져나갈 수 있는가 (안드로이드)

실패 화면은 WebView 를 트리에서 뺀 상태다. 셸이 이때도 뒤로가기를 잡으면 **누를 곳이 없는
화면에 갇힌다** — `다시 시도` 말고는 앱을 벗어날 방법이 없어진다.

- 웹에서 두세 화면 들어간 뒤(뒤로 갈 곳이 있는 상태) 비행기 모드로 새로고침해 실패 화면을 띄운다
  - 하드웨어 뒤로가기 한 번에 **앱이 닫힌다** (아무 반응이 없으면 회귀다)
- 실패 화면에서 `다시 시도` 로 돌아온 뒤 다시 두 화면을 옮겨 다닌다
  - 뒤로가기가 정상적으로 이전 화면으로 돌아간다 (한 번 실패했다고 계속 꺼져 있으면 회귀다)

### 되살리기를 멈추는가 (iOS·macOS)

콘텐츠 프로세스가 죽으면 셸이 다시 띄우는데, 되살린 문서가 뜨는 도중 또 죽으면 그대로 두면
끝없이 돈다. 상한은 2회다(`docs/mobile-shell.md`).

- 시뮬레이터에서 Debug → Simulate Memory Warning 을 짧은 간격으로 반복한다
  - 화면이 비어 있는 채로 무한히 깜빡이지 않는다
  - 결국 `연결에 실패했어요` 가 뜨고, `다시 시도` 로 정상 복귀한다
- 메모리 경고를 **한 번씩 여유를 두고** 준다 (매번 화면이 다 뜬 뒤)
  - 몇 번을 반복해도 실패 화면으로 떨어지지 않고 매번 보던 화면이 돌아온다

### 알림 켜기 (`mypage`)

- 권한을 거절하거나 알림 모듈이 실패해도 버튼이 `여는 중`에 멈추지 않고 바로 실패 문구가 뜬다
- 실패 문구가 한국어다 (네이티브 영문 메시지가 그대로 나오지 않는다)

## 통신 확인

- 인증과 세션 확인 흐름이 연결된다
- 원본 업로드와 합성 요청 과정에서 불필요한 고정값이 없다
- 히스토리와 마이페이지 조회가 정상 응답 또는 정상 에러를 처리한다
- 실패 시 사용자 메시지가 이해 가능하다
- 네트워크가 느리거나 서버가 죽었을 때도 화면이 망가지지 않는다

## 완료 규칙

- 직접 확인하지 않은 기능을 정상이라고 쓰지 않는다
- 통신을 실제로 확인하지 못했으면 부족한 조건을 명시한다
- 사용자 검증 없이 기능만 맞았다고 완료 처리하지 않는다
